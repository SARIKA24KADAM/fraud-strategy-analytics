# Fraud Strategy Analytics

A portfolio project for transaction fraud analytics, aligned with fraud performance management work: explore fraud by transaction type and time, compare a baseline rule with a candidate model, and assess fraud capture against alert volume.

## Dataset

Uses the public [PaySim dataset](https://www.kaggle.com/datasets/ealaxi/paysim1). Download `PS_20174392719_1491204439457_log.csv` and place it at `data/raw/paysim.csv`. This is **synthetic mobile-money data** generated by a simulator based on aggregated patterns; it is not TD data or real customer behavior ([PaySim paper](https://www.msc-les.org/proceedings/emss/2016/EMSS2016_249.pdf)). Raw data is excluded from Git.

## Run locally

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python -m fraud_strategy.prepare --input data/raw/paysim.csv --output data/processed/features.parquet
python -m fraud_strategy.train --input data/processed/features.parquet --output reports
python -m fraud_strategy.report --input data/processed/features.parquet --output reports
streamlit run dashboard.py
```

Run commands from the repository root. The pipeline uses DuckDB to read and transform the CSV, then scikit-learn to train a model. It expects PaySim column names.

## Project questions

- How do simulated fraud volume and fraud dollars vary by transaction type and hour?
- How does the simulator's existing flag perform compared with a probability model?
- At a given alert budget, how much simulated fraud is captured, and how many legitimate transactions would enter review?
- Which segments merit further validation before any controlled pilot?

## Repository layout

- `src/fraud_strategy/prepare.py`: point-in-time features and Parquet preparation.
- `src/fraud_strategy/train.py`: time-ordered model evaluation and threshold metrics.
- `src/fraud_strategy/report.py`: hourly and type-level summaries.
- `sql/fraud_strategy.sql`: DuckDB exploration queries.
- `dashboard.py`: Streamlit report viewer.
- `docs/`: strategy design, data dictionary, feature timing, governance, and role alignment.
- `config/strategy_assumptions.json`: explicit threshold/capacity assumptions.

## Guardrails and limitations

This is a learning demonstration, not a deployed control or financial recommendation. Scores are not used to automatically decline transactions. Customer friction is only approximated by legitimate alert volume; actual authentication outcomes, customer impact, review costs, and operational capacity are not present. Transaction type is only a product/channel proxy. The simulated labels cannot establish performance on real first- or third-party fraud. Production use would require representative institution data, point-in-time validation, independent model-risk review, fairness and privacy assessment, operational sign-off, monitoring, and rollback controls.

See [risk governance](docs/risk_governance.md) and [feature timing](docs/feature_timing.md).
